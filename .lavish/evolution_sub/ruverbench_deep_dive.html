RuVerBench 与 Agent-as-a-Judge 论文总结：确定性规则验证与分步轨迹核查

RuVerBench：RuVerBench: Rule-Verified Benchmarking for Tool-Using Agents（arXiv:2606.29920） Agent-as-a-Judge：Agent-as-a-Judge: Evaluate Agents with Agents（arXiv:2410.10934, Zhuge et al., 2024-10）

在评估包含数值计算、时间区间约束与多步工具调用的任务时，单纯使用大模型直接对最终回复打分（LLM-as-a-Judge）容易在时间加减或复杂优先级判断上出现评分偏差，且难以指出具体出错步骤。RuVerBench 主张将业务约束编写为可执行确定性验证函数；Agent-as-a-Judge 则通过核查中间执行轨迹（检索结果、状态更新、工具入参），按步骤定位失败原因。

1 RuVerBench：基于确定性规则脚本验证复合参数

① 时间与数值算术校验

用代码函数直接验证 end_time - start_time == duration_min、提前预热偏移量（start_time = base_start - preheat_min）以及跨午夜时间区间重叠关系，避免大模型裁判算错时间差。

② 多源规则优先级核对

当同一字段存在多个候选来源（日常默认值、场馆经验值、用户当轮指定值）时，通过规则脚本核对最终取值是否符合预设优先级顺序。

③ 关联字段完备性检查

验证主业务存在绑定辅业务（如高清直播关联后台网盘上传）时，输出结构中的主、辅业务槽位是否同时齐备。

2 Agent-as-a-Judge：面向中间执行轨迹的分步核查

核查环节 检查的中间状态 可分离出的具体问题类型
环节 1：检索层核查 查询语句、向量召回候选行、二阶段关联表查询结果 区分“口语映射未命中”、“负向记录未排除”或“二阶段关联表漏查”
环节 2：路由层核查 当前已知槽位表、时间冲突检查结果、所选路径（FAST / SLOW） 区分“存在时间重叠或缺失参数却未发起澄清”与“信息已齐备却重复追问”
环节 3：参数合成核查 基准单据字段 + 对话修改量 + 场馆预热偏移 → 最终工单 JSON 区分“预热时间未叠加到总时长”或“多规则冲突时取错优先级”

3 可借鉴的评测做法

  • 结构化槽位与时间计算统一采用代码校验：凡涉及字段相等、时间区间关系和时长加减的判据，均使用确定性 Python 函数评分。
  • 输出分阶段错误分布：对未通过样本按“检索漏召回”、“快慢路径判断错误”、“参数计算错误”自动归类统计，便于针对性改进对应模块。
