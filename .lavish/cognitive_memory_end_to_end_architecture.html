跨会话记忆数据集生成、记忆萃取与检索注入

本方案围绕多轮对话中的长期个性化理解需求，系统构建了从跨会话记忆数据集生成（由 PersonaHub 粗粒度画像逐步扩充至多会话时间链）、三层认知记忆萃取与双索引目录存储算法（事实记忆动态演化、工作记忆静态账本、经验记忆澄清归纳），到短窗口滑动向量匹配与三层记忆差异化检索注入的完整技术闭环。

模块一 · 数据集生成 cross_memory_data
从 PersonaHub 初始粗粒度用户画像出发，逐步补充完善业务偏好、口语习惯与历史工单库，构造跨周期 16~20 场会话时间链与多轮对话。
模块二 · 记忆萃取与存储 memory_system (Extraction & Storage)
区分三层记忆动静态生命周期（从形成、强化、艾宾浩斯遗忘衰减到冲突归档），采用分层文件夹目录配合“左列结构化槽位 + 右列短语向量”双索引落盘。
模块三 · 记忆检索与注入 memory_system (Retrieval & Injection)
采用 6~10 字滑动窗口向量匹配（Max-Pooling + 窗口级局部否定隔离），并针对事实记忆（二跳 SELECT）、工作记忆（动态时间窗 + 两阶段消歧）与经验记忆（一跳直达）执行差异化检索注入。
01

整体方案架构总览

End-to-End Architecture Overview

整套方案由三个核心环节组成：首先在数据集生成阶段，将 PersonaHub 粗粒度用户描述逐步扩充为具备长期习惯与动态事件的时间链会话集；其次在记忆萃取与存储阶段，按事实记忆（动态投票晋升与遗忘衰减）、工作记忆（静态工单流水账）与经验记忆（慢路径纠偏归纳）的动静态特性分类萃取，落盘为树形文件夹目录与 SQLite“左列结构化槽位 + 右列自然语言短语向量”双索引；最后在检索注入阶段，通过短窗口滑动向量匹配定位候选记忆，并按三层记忆各自专属的检索逻辑组装上下文注入对话理解流程。

02

跨会话记忆数据集生成

From PersonaHub Seeds to Longitudinal Session Timelines

为了真实模拟用户在长周期交互中“习惯逐步建立、口语高度省略、近期工单跨日指代、特殊经验动态演进”的过程，数据集生成采用从 PersonaHub 初始粗粒度画像出发、自底向上分步扩充至完整时间链的四步构造流程：

Step 1：PersonaHub 初始粗粒度画像筛选 初始种子

从开源 PersonaHub 数据集中筛选具有代表性职业特征与移动通信诉求的粗粒度人物种子（raw_personas.json，仅包含简短的一句话人物身份背景描述，如“常在各场馆奔波的赛事主播”、“跨园区通勤的研发工程师”）。

Step 2：多维结构化画像骨架扩充 (PersonaGenerator) 逐步完善设定

在粗粒度种子基础上，结合合规业务支撑矩阵与哈希均匀采样，调用大模型一步步补充完善出结构化的 persona_skeleton.json：明确该用户的主支线常用应用与业务类型（如抖音开直播、腾讯会议等）、默认画质与时延偏好、固定周期时段、常去场所/移动场景，并为其配备 6 大维度的个性化口语同义表述库。

Step 3：跨周期会话时间链构造 (DynamicTimelinePlanner) 16~20 场时间链

依托扩充好的画像骨架，同时挂载独立的工作记录账本（WorkingRecordsLedger）与经验规则库（ExperienceBank），在跨数周的时间轴上规划 16~20 场有严格时序依赖的会话时间链：合理穿插早期偏好建立、中期临时场景覆写、历史工单跨日回溯/消歧、以及慢路径澄清学习到快路径复用的完整演进链条。

Step 4：状态演进追踪与多轮对话生成 (MemoryTracker & DialogueGenerator) 对话渲染与校验

沿构造好的时间链逐场推进，MemoryTracker 实时计算每场会话前后的标准记忆状态快照（snapshot_before / gold_state_after），随后调用 deepseek-v4.1-flash 将结构化会话蓝图渲染为自然口语多轮对话（sessions.jsonl），并由 QCValidator 校验时间算术恒等（end - start == duration）与最小业务意图完整性。

三层记忆萃取、生命周期算法与双索引目录存储

Three-Tier Memory Extraction, Lifecycle Algorithms & Dual-Index Storage

每次会话结束时，系统严格区分三层记忆的动静态属性与生命周期规律，并在底层同时维护左侧结构化槽位列（供 SQL 精确过滤与整行读取）与右侧短语向量列（仅对 4~10 字高纯度自然语言短语编码 1024 维 Embedding），配合分层文件夹目录树实现可解释、可追溯的结构化存储。

2. 记忆生命周期管理算法（从形成、强化、衰减到遗忘归档）

记忆的形成、强化与冲突归档流转机制 Lifecycle State Machine
  • 记忆形成（显式直通 vs. 隐式初筛）：用户在对话中明确声明长期规则时（如“以后我说老规矩就按这个来”），直接赋予生效状态 active；普通日常对话中首次隐式出现的偏好先记为初筛候选 candidate (vote=1)，含“临时、就这次”的单次变更仅记为 temporary 隔离旁路。
  • 记忆强化（跨会话复现与关联规律沉淀）：当相同偏好在后续会话中再次复现，累计正向票数达到阈值（votes ≥ 2）即由 candidate 晋升为 active，三次及以上复现升级为稳固偏好 reinforced；同时对多次会话中稳定共现的“业务→默认应用”与“业务→固定时段”自动沉淀出关联记录（service_to_app / periodic_preference）。
  • 冲突更新与遗忘归档（Dispute & Archive）：当用户显式纠偏或养成新习惯替代旧习惯时，原冲突记录转入争议状态 disputed 或归档状态 archived；长期未复用且保持率衰减至阈值以下的候选记忆同样自动归档遗忘，退出在线检索池。
艾宾浩斯遗忘衰减与访问热度量化公式 Retention & Heat Model
1. 累计强化次数与记忆稳定性因子 $\kappa = 0.8$
$$n = \max(0, \text{pos\_votes} - 1) + \text{reuse\_count}, \qquad S(n) = 1.0 + \kappa \cdot \ln(1 + n)$$
符号释义：$n$ 为累计有效强化次数；$\text{pos\_votes}$ 为跨会话正向提及投票数（扣除首次建档的 1 票）；$\text{reuse\_count}$ 为在线检索命中复用次数；$S(n)$ 为记忆稳定性因子；$\kappa$ 为强化增益系数（默认 $0.8$，$n$ 越大记忆越稳固）。
2. 艾宾浩斯时间保持率公式 $\lambda = 0.03/\text{d}$
$$R(t, n) = \exp\!\left(-\frac{\lambda}{S(n)} \cdot \Delta\text{days}\right)$$
符号释义：$R(t, n) \in (0, 1]$ 为当前时刻 $t$ 的记忆保持率；$\lambda$ 为基础遗忘衰减率（事实记忆默认 $0.03/\text{天}$，工作记忆 $\lambda=0$ 不衰减）；$\Delta\text{days}$ 为距上次更新或访问的间隔天数。
3. 7天半衰期访问热度公式 $T_{1/2} = 168\,\text{h}$
$$\text{heat}_{\text{eff}} = \text{heat} \times 0.5^{\Delta\text{hours} / 168}$$
符号释义：$\text{heat}_{\text{eff}}$ 为当前有效访问热度；$\text{heat}$ 为基准热度（每次检索命中触发复用回调时提升 $+0.05$，上限 $1.0$）；$\Delta\text{hours}$ 为距上次访问的小时数，$T_{1/2} = 168\,\text{h}$（7天）为热度半衰期。

04

短窗口滑动向量检索与三层记忆分流注入

Sliding-Window Vector Matching & Tiered Memory Retrieval

在线检索不预先猜测查询哪张子表，而是将该用户的全部短语向量（单用户约 10~30 条，每条自带 subtype 标签）置于统一短语向量池。系统先通过短窗口滑动向量匹配（Sliding-Window Vector Matching）解决开放口语长句的局部语义对齐与局部否定隔离问题，随后根据命中的 subtype 标签，按三层记忆各自不同的检索逻辑分流取数并组装注入上下文。

1. 短窗口滑动向量匹配算法（解决无标点长句稀释与否定误伤）

传统标点切分 / 整句 Embedding 的局限 痛点剖析
  • 无标点长句切不开：语音转写或口语输入常一逗到底（如“今天我不去滑雪基地了改在酒店房间里趁着中午那个例行档期把抖音开直播保障开上”），纯靠标点规则切分直接失效。
  • 整句向量语义被稀释：30~40 字长句包含四五个实体，整句 Embedding 与库内 4~8 字短语（如 “午间例行”）算余弦相似度会被拉低至阈值以下。
  • 否定词污染全局：前半句“不去滑雪基地”若不精确定界，容易误将整句判定为否定或误伤后半句的正常意图。
短窗口滑窗向量匹配 + 窗口级局部否定隔离 核心泛化算法
  • 6~10 字滑动窗口 + Max-Pooling：由于库内右侧短语长度集中在 4~10 字，采用长度 8~10 字、步长 4 字的滑动窗口切分长句（约 6~8 个短窗口，单 Batch 一次编码），每个候选短语取所有窗口的最大余弦相似度（配合双字切块跨度匹配 _fuzzy_phrase_match）。
  • 窗口级局部否定隔离：哪个滑窗命中了短语，仅检查该滑窗内部及前 2~3 字局部范围是否含否定词（不/别/取消/改用），仅淘汰被否定的当前窗口短语（施加 0.15x 衰减），绝不污染其他肯定窗口。
滑窗序号 截取的 8~10 字原话滑动窗口 命中的库内右侧短语与最高余弦分 窗口局部正负判定与同行左列字段提取动作
窗口 #1 今天我不去滑雪基地了 露天高山滑雪训练基地 (cos = 0.83) 含局部否定词“不去” → 窗口级局部否定淘汰（negated_scenes），不污染后续窗口
窗口 #3 了改在酒店房间里趁着 外勤驻地酒店 (cos = 0.85) 肯定窗口 → 读取命中行左列：scene_col = "外勤驻地酒店"
窗口 #5 趁着中午那个例行档期 午间例行 (cos = 0.89) 肯定窗口 → 读取命中行左列：time_window_col = "12:30-13:30"
窗口 #7 期把抖音开直播保障开上 抖音 / 开直播 (cos = 0.91) 肯定窗口 → 读取命中行左列：app_col = "douyin", biz_col = "openlive"

2. 三层认知记忆的差异化检索与上下文注入方案

滑窗匹配在统一短语向量池中命中候选节点后，系统根据节点所属的记忆层级（factual_memory / working_memory / experiential_memory），分别执行三种不同的检索与上下文组装逻辑：

统一短语向量池 + 滑窗匹配
输入长句 → 8~10字滑窗 (步长4)
  • • Max-Pooling 计算各滑窗最高余弦分
  • • 窗口级局部否定隔离淘汰否定项
按命中的 subtype 标签三路分流：
1. preference (事实记忆)
2. working_record (工作记忆)
3. experience (经验记忆)
路径一：事实记忆检索 — 一跳读取左列字段 → 二跳关联表补全 → SQL SELECT 唯一主记录
• 一跳提取：命中 periodic_preference("午间例行") 读取 time_window="12:30-13:30"；命中 expression 读取 target="50ms"
• 二跳查询：经 service_to_app / periodic_preference 补全 (app, biz, scene)，执行 select_by_slots 查 preferred_value
