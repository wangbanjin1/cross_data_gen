后台规则长句直接拼接进台词（006 号样本等生硬台词治理）

2026-09-28 修复

现象：在 006、003、009 等地点驱动型画像中，用户台词中直接塞入了后台规划的条件规则长句（如“当上午09:00-11:00进入道路巡逻线、事故现场或应急集结区等移动执勤弱网空间时，触发现场取证、即时通信、事件上报、地图导航与位置共享任务。”），拼出诸如“今天又到[长句]办事了，这次按上次的来”的极度生硬、违背日常口语的句子。

产生原因：画像骨架中的 trigger_condition 是一整段业务规划描述，时间线规划器将其直接透传为了场景地点 scenario_env，而保底模板直接对其进行了机械字符串拼接。

解决办法：
1. LLM 语义提炼为主：针对多样化未知的职业背景，调用大模型从任务名与场景长句中提炼出 1 个 3~7 字纯名词短语（如“道路巡逻现场”、“社区走访现场”），严禁生成包含从句的非地名文本；
2. 规则安全兜底：若 LLM 响应异常或无网络，自动走正则与关键词兜底，确保流水线不中断；
3. 模板重构与台词拦截：保底模板重构为“今天在{env}，这次按上次的来”，彻底移除“办事了”等生硬词汇；并在后处理中增加对后台规则词的过滤拦截；
4. 全量数据清洗：对当前生成的 20 个画像中受影响的 51 处场景与 147 处台词进行了全面清洗修复。

候选记忆未确认即标记为生效（provisional 提前标记 memory_filled）

2026-09-28 修复

现象：隐式归纳首次出现后，记忆状态应为 provisional（候选状态），代表单次习惯观察；但在随后的复用会话中，程序提前将其标注为 memory_filled（已生效记忆），跳过了用户确认过程。

解决办法：依据会话前置快照 snapshot_before.status 进行状态分流：当状态为 provisional 时，标注来源必须为 History（历史推导），待用户第 2 轮确认后才升级为 active；只有此前已经是 active 状态的记忆，才允许使用 Memory 来源。

    "application_name": "腾讯会议",
    "resolution": "1080p",
    "source": "Memory" // 错误：候选状态未确认，提前标为 Memory
  }
}]
// 质检报错：provisional 状态不允许直接标记为 memory_filled
解决后的规范表现

// 规范：来源溯源至历史记录，待用户确认后才生效

// 标注来源标记为 History，状态为 in_progress

// 后置记忆状态正式由 provisional 升级为 active

对话时间标注向首轮提前写入（时序跨轮早泄）

2026-09-28 修复

现象：用户在第 1 轮只说了“今晚8点要在腾讯会议上开个视频会”，并未说明持续多长时间；但首轮的结构化标注中却提前写入了后续轮次才讨论确定的结束时间（22:00）和持续时长（120分钟），破坏了对话状态追踪（DST）的时序因果。

解决办法：严格实施逐轮隔离。第 1 轮仅标注已明确说出的 start_timestamp，未提及的画质、时延与时长记入 requested_params 待追问列表；等到第 2 轮用户澄清并明确时长后，再行计算并写入结束时间与时长。

域外拒绝会话中动作标签与台词语义矛盾

2026-09-28 修复

现象：模板规划为域外诉求拒绝（T1-2），数据动作标签标记为 Reject_Request，但大模型生成的自然语言台词却是正常答应并受理（如“好的，这就为您派师傅修宽带”），导致标签与对话台词严重矛盾。

解决办法：在提示词中强制注入域外目标拒识约束（ood_goal），并在质检流程中增加 template_semantic_alignment_check 自动化规则，凡动作标记为 Reject_Request 时，Agent 台词必须包含明确的不可受理说辞。

出现问题时的台词表现
// 会话模板：T1-2（域外拒绝）
// 动作标签：Reject_Request
User: "我家宽带光纤断了，上不了网，帮我找个师傅上门维修。"
Agent: "好的，已为您登记家庭宽带上门检修工单，维修师傅将在2小时内联系您，请保持手机畅通。"

// 缺陷：标签判定为无法受理并拒绝，但台词却在满口承诺受理，标签与台词矛盾
解决后的规范台词表现
// 会话模板：T1-2（域外拒绝）
// 动作标签：Reject_Request
User: "我家宽带光纤断了，上不了网，帮我找个师傅上门维修。"
Agent: "抱歉，我这边主要负责移动网络通信保障，无法直接受理家庭宽带的光纤装维报修。建议您拨打10086宽带专线处理。"

// 规范：台词明确表达拒绝受理并说明范围，与 Reject_Request 动作严格一致

2026-09-28 修复

现象：在早期的建联会话中，用户自始至终只提过官方标准名“腾讯会议”；但到了后续的复用会话首轮，用户台词却突然冒出“用tencentmeeting开会”或“用企鹅例会保障”，缺乏任何前置交互与登记依据。

复用已知参数时机械复读与口语词汇失真

2026-09-28 修复

现象：在已经记录了习惯配置的复用会话中，用户本应只说“老规矩”，却把 1080p、50ms、120分钟等全量参数又逐字复读了一遍，失去了记忆调取的实际意义；同时生成了“顶格清晰度”（易与2K/4K混淆）、“零卡顿”（物理不可能）等失真词汇。

解决办法：通过 expression_vault.json 规范口语映射范围；在复用会话中强制省略已知槽位，用户第 1 轮仅凭暗号（“老规矩”）和代称发起，由助手主动从历史记忆中调取配置向用户反问确认，用户第 2 轮只需简要确认。

模板编号与实际交互轮数/意图数错配

2026-09-28 修复

现象：主线 2 轮 1 意图会话误套用了双意图模板编号（T2-4）；支线会话在加入模糊词澄清对话后交互轮次扩展到了 3 轮，但模板 ID 仍保留为 2 轮编号（T2-2），导致骨架签名出现 T2-2|3|1|... 冲突，自动化校验报错。

解决办法：建立模板规格强校验规则（template_spec_check），校验模板前缀、声明轮数、实际交互轮数、声明意图数、实际意图数完全一致：2 轮 1 意图必须使用 T2-1，3 轮 1 意图必须匹配 T3-1。

出现问题时的模板规格
// 会话：支线 1 模糊澄清会话
"session_meta": {
  "template_id": "T2-2",   // 错误：前缀 T2 代表 2 轮模板
  "round_count": 3         // 实际对话交互已扩展为 3 轮
}
// 骨架签名生成：T2-2|3|1|SUB_001|Single...
// 质检报错：template_spec_check failed 
// (模板 ID 前缀 T2 与 实际交互轮数 3 轮产生错配冲突)
解决后的规范模板规格
// 会话：支线 1 模糊澄清会话
"session_meta": {
  "template_id": "T3-1",   // 规范：前缀 T3 与 3 轮交互精确匹配
  "round_count": 3
}
// 骨架签名生成：T3-1|3|1|SUB_001|Single...
// 质检结果：template_spec_check passed
// (模板编号、轮数与意图数完全一致，通过校验)
