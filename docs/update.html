架构设计与模板拓扑规范

解析 12~16 轮动态规划、16 槽位模板全景因果拓扑（Causal DAG）与安全裁剪机制

会话总长度规划机制（12~16 轮动态浮动）与 16 槽位模板分布拓扑规范详解

架构拓扑 2026-10-10 架构解析
背景与问题

在审查生成的样本数据时发现，各画像的会话总长度均在 14 轮左右浮动（集中在 12~16 轮之间）。需要透彻明确：会话数量是如何确定的？是否存在写死的流程？模版在时间轴上的分布规律（拓扑结构）背后的因果逻辑是什么？

原理与机制
1.
会话总长度动态规划公式：在 src/core/timeline_planner.py 中，采用公式 target_count = 12 + (uid_num % 5)。由于 uid_num % 5 在 0~4 均匀分布，目标轮数均匀离散为 12, 13, 14, 15, 16 轮，算术均值恰好为 14 轮，避免固定单一的会话轮数；
2.
16 候选槽位全景拓扑（Causal DAG）：系统在 src/templates/timeline_blueprints.py 中定义了严格满足长程记忆因果律的 16 槽位候选矩阵，覆盖四大演进阶段：
•
阶段一（记忆建立与歧义消解）：S1 主线首次建联 (T2-1) → S2 支线1弱网别名消歧 (T2-2/T3-1)；
•
阶段二（多线交织与记忆固化）：S3 主线首次强化 (T2-1) → S4 支线2建联 → S5 域外干扰拒识 (T1-2) → S6 支线1复用强化；
•
阶段三（记忆复用与时长变更）：S7 主线复用并延长时间 (T2-5) → S8 主线常规强化 → S9 支线2强化 → S10 混合诉求一办一拒 (X-1)；
•
阶段四（突发事件纠偏与恢复闭环）：S11 恶劣天气临时纠错 (T2-3) → S12 纠偏中主线复用 → S13 支线1复用（隔离验证：确保不被主线纠偏污染） → S14 单轮干扰 (T1-1) → S15 事件失效主线基线恢复 (T2-1) → S16 终态持续复用；
3.
因果闭环安全裁剪机制：当 target_count 小于 16 时，系统优先安全剥离非核心节点（如 extra_reuse S16、dist_normal S14、sub2 S4/S9），核心闭环 8 大节点（S1, S2, S3, S5, S7, S10, S11, S15）全部保留，保证因果逻辑链条完整闭环。

数据多样性机制与提示词规则

双层解耦：基于数学取模/哈希的多样性发散机制 与 提示词/代码约束规则对照

全流水线“多样性离散处理”与“提示词约束规则”规范解耦

多样性规范 2026-10-10 架构解析
背景与问题

整个数据生成流水线中，哪些维度做了随机/多样性处理以保证百人百面？哪些逻辑是在 Prompt 或代码中严格写死的？二者的边界与设计原则是什么？

原理与机制

为同时保证“评测金标准确无幻觉、因果可复现”与“自然语言多样性、情境丰富”，流水线采用了双层解耦架构：

多样性处理层（通过取模/哈希与LLM生成，保障分布均衡与情境丰富）：

1.
声明模式 50/50 划分：uid_num % 2 == 1，奇数显式声明，偶数隐式归纳；
2.
触发类型 1:1:1 轮转：uid_num % 3，周期时间驱动 / 现场任务驱动 / 物理地点驱动均衡分布；时间驱动下再下钻为 daily(3个时段)、weekly(8类周组合)、monthly(月度节点)；
3.
小记忆点 6 维哈希抽样：利用 hashlib.sha256(uid:type)，从应用昵称、业务默认应用、画质别名、时延别名、时长别名、个性化周期表达 6 大维度中动态选择，保证每个人物的小记忆类型各不相同；
4.
会话总轮数浮动：12 + (uid_num % 5) 产生 12~16 轮动态浮动；
5.
现场地点提炼与台词发散：LLM 动态提取 3~7 字自然地点名词（如“沿海巡逻岸线”），并根据各角色 speech_style 发散多轮口语化台词。

二、提示词约束规则（严格约束，确保合规与基准严谨）：

1.
业务与 App 白名单写死：仅限 7 项标准通信业务（开直播、看直播、视频通话等），严禁大模型捏造不支持的业务；
2.
参数别名对齐律写死：1080p 只能叫“1080p原画/超清”，严禁夸大为“顶格画质”；50ms 严禁夸大为“零卡顿”；整条时间线必须全局一致，严禁同一主线在不同会话中跳变称谓；
3.
去系统术语写死：严禁台词中出现“长期偏好”、“元指令”、“触发槽位”等程序员词汇，强制使用“记住这个习惯哈”等真实口语；
4.
冷启动与最小表达律写死：S1 首次建联严禁提生僻别名或未生效的个性化表达；复用会话严禁只说“老规矩开保障”，必须说出应用+业务并省略已知参数。

后台规则长句直接拼接进台词（006 号样本等生硬台词治理）

缺陷修复 2026-09-28 修复
问题现象

在 006、003、009 等地点驱动型画像中，用户台词中直接塞入了后台规划的条件规则长句（如“当上午09:00-11:00进入道路巡逻线、事故现场或应急集结区等移动执勤弱网空间时，触发现场取证、即时通信、事件上报、地图导航与位置共享任务。”），拼出诸如“今天又到[长句]办事了，这次按上次的来”的极度生硬、违背日常口语的句子。

根因排查

画像骨架中的 trigger_condition 是一整段业务规划描述，时间线规划器将其直接透传为了场景地点 scenario_env，而保底模板直接对其进行了机械字符串拼接。

解决办法
1.
LLM 语义提炼为主：针对多样化未知的职业背景，调用大模型从任务名与场景长句中提炼出 1 个 3~7 字纯名词短语（如“道路巡逻现场”、“社区走访现场”），严禁生成包含从句的非地名文本；
2.
规则安全兜底：若 LLM 响应异常或无网络，自动走正则与关键词兜底，确保流水线不中断；
3.
模板重构与台词拦截：保底模板重构为“今天在{env}，这次按上次的来”，彻底移除“办事了”等生硬词汇；并在后处理中增加对后台规则词的过滤拦截；
4.
全量数据清洗：对当前生成的 20 个画像中受影响的 51 处场景与 147 处台词进行了全面清洗修复。

候选记忆未确认即标记为生效（provisional 提前标记 memory_filled）

缺陷修复 2026-09-28 修复
问题现象

隐式归纳首次出现后，记忆状态应为 provisional（候选状态），代表单次习惯观察；但在随后的复用会话中，程序提前将其标注为 memory_filled（已生效记忆），跳过了用户确认过程。

解决办法

依据会话前置快照 snapshot_before.status 进行状态分流：当状态为 provisional 时，标注来源必须为 History（历史推导），待用户第 2 轮确认后才升级为 active；只有此前已经是 active 状态的记忆，才允许使用 Memory 来源。

对话时间标注向首轮提前写入（时序跨轮早泄）

缺陷修复 2026-09-28 修复
问题现象

用户在第 1 轮只说了“今晚8点要在腾讯会议上开个视频会”，并未说明持续多长时间；但首轮的结构化标注中却提前写入了后续轮次才讨论确定的结束时间（22:00）和持续时长（120分钟），破坏了对话状态追踪（DST）的时序因果。

解决办法

严格实施逐轮隔离。第 1 轮仅标注已明确说出的 start_timestamp，未提及的画质、时延与时长记入 requested_params 待追问列表；等到第 2 轮用户澄清并明确时长后，再行计算并写入结束时间与时长。

域外拒绝会话中动作标签与台词语义矛盾

缺陷修复 2026-09-28 修复
问题现象

模板规划为域外诉求拒绝（T1-2），数据动作标签标记为 Reject_Request，但大模型生成的自然语言台词却是正常答应并受理（如“好的，这就为您派师傅修宽带”），导致标签与对话台词严重矛盾。
